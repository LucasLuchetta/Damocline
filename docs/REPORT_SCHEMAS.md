# HTTP run report schemas

## Supported versions

The engine currently emits schema v30. The `insights` reader accepts v1 through v30 and rejects unknown future versions. Historical reports are read into the current Go model without rewriting the original file; fields introduced after a report's schema version remain absent and are not evidence of a measured zero.

| Version | Fields introduced or versioned | Compatibility meaning |
| --- | --- | --- |
| v1-v2 | Base run metadata, configured workload, request and journey summaries. | Fields not present in a particular saved report remain unknown. |
| v3 | Generator runtime summary. | Missing generator observations are not zero consumption. |
| v4 | Observation horizon and generator process CPU/RSS evidence. | Wall-clock elapsed time and workload observation time are separate. |
| v5 | Weighted profile definitions and per-profile journey summaries. | Weights express the declared mix, not proof of representativeness. |
| v6 | Conditional IID-assumption P95 rank interval. | An absent interval is not a zero-width interval. |
| v7 | Per-step HTTP client phase counts and timing totals. | Fields describe client-observed phases and are unknown in older reports. |
| v8 | Exact status and structured HTTP outcome counters. | Missing historical counters are unknown, not zero failures. |
| v9 | Workload-mix provenance labels. | A label is declared provenance and does not validate a mix. |
| v10 | Generator sampler cadence, gap and collection cost. | Missing cadence and cost are unavailable evidence. |
| v11 | Opaque workload fingerprint. | A fingerprint is a declared-shape digest, not a signature or endpoint attestation. |
| v12 | Bounded response-body completion, interruption, size and oversize observations. | A recorded complete zero-byte response differs from a report that predates body observations. |
| v13 | Per-step request and explicit-profile completed-journey evidence in observation windows. | Missing or inconsistent current window ledgers are invalid; older reports cannot support windowed per-step conclusions. |
| v14 | Explicit `connection_policy` (`reuse` or `new_per_request`) applied by the engine and included in workload fingerprints. | A missing policy in an older report is unknown; only schema-v14 reports record this comparison dimension. |
| v15 | Optional controlled-reference evidence with independent server ledger counters, bound to the calibrator fixture fingerprint. | Accepted only for the calibrator-owned loopback soak; it does not attest arbitrary endpoints or external report authenticity. |
| v16 | External-cancellation count for planned arrivals not admitted before the schedule ended. | Required in v16, including when zero; absent in older schemas and never inferred as zero. Distinct from scheduler-late and worker-busy drops. |
| v17 | Count of arrivals admitted by the scheduler's worker handoff. | Required in v17, including when zero; absent in older schemas and never inferred as zero. Current arrival reports reconcile planned = admitted + dropped and admitted = started iterations. |
| v18 | Effective generator CPU capacity and source/known metadata. | Unknown entitlement is distinct from unlimited capacity and prevents positive quality. |
| v19 | Logical CPU count independently from GOMAXPROCS and effective CPU quota. | Missing or impossible logical CPU evidence is not inferred from other CPU fields. |
| v20 | Versioned HTTP failure classification with DNS-resolution and connection-establishment failure counters, retained as subcategories of transport failures. | The explicit classification version distinguishes measured zero counts from reports that predate the evidence. TLS and network timeouts remain separate categories; TCP resets after connection are not mislabeled as connection-establishment failures. |
| v21 | Optional bounded `think_time_range` or discrete `think_time_samples` and `workload_seed` in run configuration, with per-profile overrides. | A variable policy requires a nonzero seed. Older reports have no variable-timing provenance; fixed-pause behavior remains readable. |
| v22 | Completed journey counters and latency distributions in each observation window, including legacy single-workflow scenarios. | Window journey counts reconcile with run-level journeys; explicit profile windows also reconcile with the aggregate window ledger. Older reports cannot establish full-journey window SLOs. |
| v23 | Optional local generator CPU/RSS abort policy and first consecutive-sample trigger evidence. | CPU is normalized to detected generator capacity; RSS and CPU describe the generator process, never the target. Sampling can miss peaks, and configured limits are operational aborts rather than target-capacity thresholds. |
| v24 | Identifies explicitly configured synthetic cleanup steps in run step evidence. | Cleanup outcomes remain ordinary HTTP observations; process termination or exhausted drain time can still leave data behind. |
| v25 | Optional bounded, timestamped Prometheus-text application-metrics timeline on each run/phase report, with source, interval, aggregate samples and collection failures. | Labels and URL query credentials are not retained; auxiliary metrics scrapes are not part of load counters, quality verdicts or causal findings. Timeline completeness is independently marked and must be interpreted manually. |
| v26 | Weighted workflows are selected per journey start in closed-loop and open-arrival runs; per-profile selection counts and distinct observed-actor counts are persisted. | Profile selection and worker-started journeys reconcile with aggregate scheduler/journey ledgers. Historical reports retain their original profile assignment semantics. |
| v27 | Named workflow session scopes are recorded when per-workflow cookie sets are configured. | Cookie values and environment-variable names are never stored; the scope names are part of the declared workflow configuration. |
| v28 | Optional `max_connections_per_host` and per-step connection acquisition, reuse, and delayed reused-connection observations. | Acquisition timing is client-observed. Reused connection acquisition of at least 10 ms can indicate client transport queueing but does not prove pool exhaustion or target saturation. Explicit caps are outside the fixed calibration matrix. |
| v29 | Per-metric-set count of requests rejected locally during expanded URL/header/body construction because of bounded template output. | These failures did not reach the HTTP target and invalidate delivery attribution; the count contains no expanded values. |
| v30 | Declares nearest-rank latency percentiles and the exact binomial order-statistic method for 95% p95 rank intervals, with the IID/stationarity assumption. Exact intervals are marked per metric set; historical normal-rank intervals remain explicitly labeled as approximations. | Exact binomial rank coverage is conservative under IID observations. Temporal or actor-level dependence can still make the nominal interval under-cover; a deterministic clustered simulation demonstrates this limitation. Computation is bounded to one million samples; above that, no rank interval is emitted. |

For schema-v11 and newer reports attached to calibration, workload-shape assessment recomputes the fingerprint only for the persisted single-step `GET /work` reference subset. The run fingerprint covers declared step status, text and JSON scalar assertions, but their values are not persisted in reports. Schema-v14 reports record whether the engine reuses connections or opens a new connection per request. The fixed calibration covers reuse only; `new_per_request` is outside its envelope. Other request shapes remain unverified because reports do not retain all request templates or values needed for safe reconstruction. A matching fingerprint is not a signature, endpoint attestation, or general workload-equivalence proof. Schema-v15 and newer reports may report `VALID_WITHIN_ENVELOPE` only for the calibrator's own 30-second loopback soak when calibration, same-executable identity, generator health, response observations and independent server counters reconcile. This qualifies that controlled fixture execution only.

## Reader and fixture policy

Golden JSON fixtures in `internal/insights/testdata/reports/` cover every currently supported version. Tests verify reader acceptance, JSON round-trip stability, and preservation of a version-specific field at each schema milestone. Separate tests verify that unknown future versions are rejected, schema-v11 absence of body fields is not reinterpreted as an observed zero-byte body, schema-v20 failure-classification metadata is required, schema-v22 window journey evidence round-trips, schema-v27 workflow session scopes remain bounded, schema-v28 transport limits are retained, and schema-v30 statistical method metadata is required.

No automatic migration rewrites historical artifacts. Consumers must use the report version to determine whether a field was recorded. A reader update must add support and a fixture for a new schema version before increasing the accepted ceiling.

JSON report output is written to a restricted temporary file in the destination directory, synchronized, and then replaced. Unix also synchronizes the parent directory; Windows requests write-through replacement. Serialization and the 16 MiB limit are checked before the destination is touched. Serialization, temporary-file, or rename failures leave the existing report untouched. If Unix directory synchronization fails after rename, the replacement has already occurred and the returned error states that crash durability could not be confirmed. Unix applies mode `0600`; on Windows, access control depends on the destination directory's inherited ACL because Go's permission bits do not set Windows ACL entries. Filesystem and hardware failure guarantees remain those of the underlying platform and storage device.

`report save --file artifact.json` copies a valid JSON object byte-for-byte into `.damocline/reports` (or an explicit `--dir`). Its filename contains a UTC timestamp and SHA-256 digest; `report history` verifies each digest and prints local metadata. The archive stops accepting new entries at 100 files or 512 MiB. It never removes reports automatically: `report prune --keep N` removes older entries only when explicitly run, and `report delete --id ID` removes one exact entry. Saving does not rewrite or redact arbitrary input; archive only sanitized Damocline evidence intended for local retention.

`report export --file artifact.json --out redacted.json` accepts a validated run, closed-loop campaign, open-arrival campaign, closed-loop exploration, or open-arrival exploration and writes `damocline-redacted-evidence-v2`. This allowlist format preserves bounded workload units, outcome and aggregate request/journey metrics, the fixed profile-selection enum and profile selected/start counts, step/workflow aliases, observation windows, arrival/scheduler accounting, generator utilization ratios, external scrape timing/counts, and fixed statistical-method identifiers with exact p95 IID bounds when available. It removes target origins and paths, arbitrary scenario/profile/step/metric names, free-text notes/warnings/reasons, revisions, fingerprints, environment declarations, and absolute timestamps. External metric names and scalar values are omitted because custom telemetry can contain identifiers. The export is descriptive only: native validators and capacity assessors reject it by format; users must retain the original private artifact for full offline audit. Export replaces only the explicitly selected destination atomically and refuses an input/output path alias.

Campaign reports use an independent schema counter. Schema v3 records successful journey throughput spread. Schema v4 adds an optional final 10-second to 3-minute soak after all independent trials, with exact schedule validation and a recomputed coarse journey/window drift screen. Schema v5 persists bounded drift-screen thresholds; offline campaign validation recomputes every observation/soak classification with the saved policy and rejects invalid or missing policy values. Schema v6 can record an explicitly enabled staging long-run mode, the declared environment and an explicit wall-time budget; it raises observation/soak phase limits to 30 minutes and the overall cap to 2 hours. Schema v7 can persist local generator CPU/RSS abort limits, and offline validation matches those limits against every native phase report. Schema v8 preserves a recovery phase after a spike that breaches an objective; the trial remains FAIL after recovery. Schema v9 adds cooldowns and unique trial IDs; schema v10 checkpoints completed phases with an explicitly `RUNNING` pending trial. Schema v12 can persist a closed-loop local calibration envelope, its operator-supplied source path, and whether calibration was required. Offline validation checks that the envelope contains exactly the planned base and spike VU levels, that dimension and readiness states are internally consistent, and that a required gate was READY. This is structural consistency only: the path is not an attestation and offline validation does not re-read the source artifact. Offline campaign validation checks recovery evidence, phase schedule and IDs, and treats a running checkpoint as incomplete evidence. Historical schemas retain their earlier schedules and limits. The environment is user-declared and is not independently verified.

Closed-loop exploration reports use a separate schema counter. Schema v2 persists probe and overall termination reasons, including invalid delivery, request-rate binding, wall-time exhaustion and caller interruption. The offline capacity-goal reader continues to accept schema-v1 and schema-v2 explorations.
Arrival exploration artifacts use their own schema versions; they are not HTTP run reports and do not change the run report schema version. Schema v1 retains the scheduled journey-start search bounds, worker limit, optional exact target and whether it was tested, every attempted probe, and all native run reports for each attempt. Schema v2 additionally records the requested bounds and exact calibration-qualified rates; every recorded probe must belong to that set, and offline goal assessment rejects inconsistent metadata or unqualified probes. Calibrated searches may reduce the effective maximum to the highest exact compatible matrix rate. A result bracket is descriptive evidence for that tested envelope only. Consumers must keep journey starts/s, admitted/completed journeys, VUs, and HTTP requests/s separate.

Repeated open-arrival campaign artifacts use `arrival_campaign_schema_version: 6`, independent of both HTTP run reports and closed-loop campaign schemas. Schemas 1 and 2 retain the base and spike scheduled-start rates, worker limit, workload fingerprint, declared controls, phase schedule, every native phase report and its recomputed evidence/stability labels. Schema 2 can additionally record an explicitly enabled staging long-run mode with a 30-minute observation/soak bound and 2-hour total budget. Schema 3 can persist optional generator CPU/RSS abort guardrails, which `goal` matches against every phase report offline. Schema 4 preserves and requires recovery evidence following an observed spike objective breach; the campaign remains failed after recovery. Schema 5 adds bounded cooldowns and unique trial IDs; schema 6 checkpoints completed phases and identifies a pending trial as `RUNNING`. Closed-loop campaign schema 7 supports the same generator policy, schema 8 adds failed-spike recovery semantics, schema 9 adds cooldowns and trial IDs, and schema 10 adds phase checkpoints. Earlier versions remain readable under their recorded policies. `goal` checks the exact base target and complete repeated schedule offline; a running checkpoint remains incomplete evidence. The environment is user-declared, not verified by Damocline. Ordinary native reports remain LIMITED outside the controlled calibration envelope, so a campaign PASS is not a certified capacity limit.

Offline campaign audit schema v2 adds `repeatability_evidence`: an exact two-sided 95% Clopper-Pearson interval for the terminal PASS fraction among completed PASS/FAIL trials. Aborted and nonterminal trials are excluded and counted. The interval assumes independent, stationary repeat trials and describes same-condition trial pass probability only; it is not a capacity confidence interval. Assessment schema v3 additionally records the input peak demand, growth, and reserve used to calculate `demand.target_users`; schema-v1/v2 readers can ignore those additive fields. Campaign collection assessment schema v2 preserves the same inputs when the target is missing from the supplied levels.
