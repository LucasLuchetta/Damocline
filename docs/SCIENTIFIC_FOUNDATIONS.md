# Scientific foundations and validation contract

Damocline uses established performance and queueing ideas to design measurements. A citation supports a method; it does not validate Damocline's implementation or prove a particular application's capacity. Every reported conclusion must remain conditional on the workload, environment, observation window, measurement quality, and assumptions below.

## Methods and limits

| Foundation | What it supports | How Damocline should apply it | Limit that must remain visible |
| --- | --- | --- | --- |
| [Little, “A Proof for the Queuing Formula: L = λW” (1961)](https://doi.org/10.1287/opre.9.3.383) | A relationship among long-run average work in a system, effective arrival rate, and average time in the system. | Use as a steady-state consistency check only when the same request or journey boundary is used for concurrency, throughput, and elapsed time. Use *admitted/completed* work appropriate to that boundary and reconcile in-flight work at its edges. | It is not a capacity predictor, a tail-latency model, or a way to convert VUs into people. Finite, transient campaigns do not automatically satisfy its stationarity assumptions. |
| [Schroeder, Wierman, and Harchol-Balter, “Open Versus Closed: A Cautionary Tale” (NSDI 2006)](https://www.usenix.org/conference/nsdi-06/open-versus-closed-cautionary-tale) | Open, closed, and partly open workload models can produce materially different performance conclusions; choosing a model that matches the system and workload matters. | Closed VUs model a fixed population whose next work depends on prior completion. Open arrivals model demand scheduled independently of response completion. A partly open model is useful when sessions arrive independently but their internal steps depend on prior responses and include think time. Select and name the model from observed user or system behavior. | Open and closed workloads are not interchangeable settings for the same business claim. The current engine supports closed journeys and open journey arrivals; it must not claim a fully modeled partly open population until session arrivals and within-session behavior are represented and verified together. |
| [Georges, Buytaert, and Eeckhout, “Statistically Rigorous Java Performance Evaluation” (OOPSLA 2007)](https://doi.org/10.1145/1297027.1297033) | Experimental design, startup behavior, non-determinism, independent repetitions, and statistical analysis affect performance conclusions. | Keep warm-up separate from measurement, retain every repeat, disclose the host/runtime/workload, and report variability instead of selecting the best run. Apply the experimental principles to Go and the target system, while validating the details for each environment. | The paper studies Java runtimes and does not prescribe a universal number of Go runs, a particular confidence method for HTTP percentiles, or a campaign duration. |
| [Gunther, “A General Theory of Computational Scalability Based on Rational Functions” (2008)](https://arxiv.org/abs/0808.1431) | The Universal Scalability Law relates throughput scaling to concurrency using contention and coherency terms and connects to queueing models. | Consider fitting it only after repeatable throughput measurements exist at multiple concurrency levels for the same workload and environment. Keep observed points, fit error, parameter uncertainty, and the tested range beside any fitted curve. | A good fit is descriptive evidence under its assumptions, not proof of the cause, a guarantee beyond the measured range, or a prediction that a hardware upgrade will help. Do not extrapolate a client-capacity recommendation from a short, capped, or non-stationary sweep. |
| [Dean and Barroso, “The Tail at Scale” (2013)](https://research.google/pubs/the-tail-at-scale/) | High-percentile latency matters to interactive services, and tail behavior becomes more visible in large, composed systems. | Preserve p95/p99 for requests and complete journeys, along with counts and time windows. Inspect degradation over time instead of relying on one aggregate percentile. | A p99 from a small sample is weak evidence; repeated requests in one session are correlated. A percentile alone does not identify a bottleneck or represent browser rendering and downstream work that the scenario omits. |
| [Almeida and Menascé, “Capacity Planning: An Essential Tool for Managing Web Services” (2002)](https://doi.org/10.1109/MITP.2002.1046642) | Capacity planning combines architecture and workload characterization, model parameters, model calibration, and cost/performance trade-offs. | Separate demand assumptions, measured results, model outputs, and investment choices. Compare configurations using matched workloads and evidence from each configuration. | A planning method is not an empirical measurement of an untested server size. Application, database, network, and deployment context must be represented or marked unknown. |
| [TPC Benchmark W specification](https://www.tpc.org/tpcw/specs.asp) | A benchmark can define transaction mixes and user navigation through stateful business workflows. | Use as historical design inspiration for weighted, stateful journeys, synthetic data, valid transitions, and repeatable workload definitions. Build scenarios from the target application's own sanitized usage evidence. | TPC-W is an e-commerce benchmark, not a representative mix for every application. Damocline does not claim TPC-W compliance or comparable benchmark results. |

## Measurement rules derived from these methods

1. **Define the unit first.** Name whether a scheduled arrival is a request, journey, or session. Record VUs, active workers, in-flight requests, delivered arrivals, and completed operations separately.
2. **Choose the workload model from evidence.** Use sanitized production aggregates or a documented business assumption. Record session length, transition probabilities, think-time distribution, arrival pattern, authentication state, data size, and read/write mix where they affect the result.
3. **State boundaries and invariants.** Reconcile scheduled, admitted, dropped, started, completed, failed, and unfinished work. Define whether latency includes queueing, connection setup, think time, response-body reading, and end-of-test drain.
4. **Separate warm-up from observation.** Measure steady behavior only after the selected warm-up rule is met. Retain transient behavior separately when startup performance matters.
5. **Repeat the experiment and preserve all runs.** Record environment and scenario revision, do not select the best run, and report run-to-run spread. Repetition count and duration must be justified by variability and the decision horizon, not treated as a universal constant.
6. **Match statistical methods to dependence.** The one-sided binomial bound in the current error assessment assumes stationary independent Bernoulli outcomes. Requests from the same session, time window, or deployment are often correlated. Present that bound as conditional evidence, and add time-separated trials or dependence-aware methods before treating it as a reliability guarantee. Percentile uncertainty needs its own sample-adequacy and interval method; an error-rate bound does not provide it.
7. **Treat generator limits as measurement limits.** Observe delivery delay, missed deadlines, worker shortage, generator CPU/memory/GC, and traffic-governor binding. An application failure under a client-limited or under-delivered load is not a clean estimate of the application's capacity boundary.
8. **Separate signals from causes.** CPU, memory, database waits, queue depth, and latency are observations. A bottleneck cause or an infrastructure recommendation requires a controlled comparison or enough aligned telemetry to support that inference.
9. **Plan demand; measure capacity.** Growth and reserve calculations produce a target load to validate. They do not predict how much a VPS or application can handle.

## Current evidence boundary

Merged work adds explicit arrival accounting, generator Go-runtime observations, conditional error-rate uncertainty, offline demand assessment, and goal-directed exploration. Local P0 work now also samples Windows/Linux process CPU and resident memory and reconciles a bounded separate-process reference workload. These advances do not complete scientific validation.

The current owner-goal evaluator requires Go runtime and supported OS process CPU observations, then uses provisional 90% guards for average Go-runtime CPU utilization, sampled process CPU utilization, and configured request-rate ceiling when deciding whether generator evidence is adequate. Those values are implementation safeguards, not thresholds derived from the cited papers or calibrated against a representative range of machines. They can miss brief saturation and must not be described as a scientifically established headroom margin.

| Method or capability | Current state |
| --- | --- |
| Open and closed workload execution | Implemented with explicit scheduling and delivery observations. Named weighted profiles are implemented as declared workload assumptions with deterministic selection and per-profile journey evidence; a full partly open session-arrival model is not implemented. |
| Little's Law diagnostic | Not implemented. Reports do not yet retain average in-flight requests or journeys over matching steady-state windows, so the three terms cannot be checked consistently. |
| Error-rate uncertainty | Implemented as a one-sided binomial upper bound under independent, stationary outcomes; dependence-aware confidence analysis is not implemented. |
| Latency-percentile uncertainty | Not implemented. P50/P95/P99 are point estimates; sample counts are present, but there are no confidence intervals for percentiles or run-to-run variation. |
| Universal Scalability Law or queueing-model fit | Not implemented. Do not infer capacity beyond the tested VU levels. |
| Business demand target | Implemented as a deterministic target calculation and exact bounded probe; the calculation is a load to validate, not a server prediction. |
| Sustained campaign and infrastructure alternatives | Not implemented in the merged base. Warm-up/soak/recovery orchestration, aligned dependency telemetry, and matched cost/performance comparisons remain open. |

Still required before calling a capacity level validated: a predeclared pass/fail protocol; repeated reference workloads across platforms and load ranges; measurement tolerances based on independent expected values; statistical treatment of run and time-window variation; representative session/workload models; sustained campaigns; calibrated generator-health limits; and matched infrastructure comparisons. The CI reference smoke matrix verifies bounded arrival counts, coarse controlled-latency ranges, worker underdelivery, known errors, and Windows/Linux process sampling; it does not establish timing precision or maximum load on every supported host. Until those gates are met, reports should say **observed under these test conditions** or **insufficient evidence**, never imply that the scientific references certify the software.
