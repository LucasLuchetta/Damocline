# Architecture

This document describes the current architecture and planned extensions. The measurement contract and roadmap identify which capabilities are implemented and which remain unvalidated or planned.

## The boundary

Damocline measures observed application behavior under a defined synthetic workload. It will not pretend that an external URL exposes the CPU, memory, database, or autoscaling behavior of its host. Resource correlations are possible only when optional telemetry is connected.

```text
                  Scenario + SLOs
                       |
          Capacity explorers (VU / arrival)
                 /             \
         Scheduler        Safety controller
             |                  |
     Virtual-user runtime <-----+
             |
       Native Go HTTP engine
             |
      Application under test  ----> Optional infrastructure telemetry
             |                                |
         Responses ---------------------------+
                       |
             Metrics and validation
                       |
           Evidence-based capacity report
```

## Logical components

**Scenario specification.** Versioned target, optional safe workload-revision, environment, and workload-mix provenance labels, request or journey steps, authentication references, think times, workload mode, acceptance criteria, traffic limits, and output options. Scenario files are limited to 1 MiB; parsed workloads are limited to 50 VUs, 100 RPS, three minutes, and 20 total steps. A scenario may define either one legacy journey or two to ten weighted profiles with their own named steps and optional think time. The report records configured weights, self-declared mix basis/reference and observed journey counts. A step can extract a bounded JSON Pointer or response-header value and a later step in the same journey can use it in a complete path segment, query value, header, or environment-backed body. Path segments and query values use component-specific URL escaping and cannot replace the configured origin. Steps can require bounded JSON Pointer scalar postconditions after status and text assertions; assertion values affect the workload fingerprint but are never copied into reports. An opt-in environment-backed synthetic prefix enables a new private `{{synthetic_id}}` for each journey. Explicit final cleanup steps must be DELETE requests scoped to that identifier; after external cancellation, they use only the remaining bounded drain allowance and remain subject to the request-rate governor. Cleanup is best-effort and cannot survive process termination. Mix provenance labels do not prove representativeness.

**Workload scheduler.** The engine supports closed-loop virtual users and open-loop journey arrivals. It tracks scheduled starts, scheduler admissions, worker-started iterations, late and worker-busy drops, externally cancelled starts not admitted, scheduler lag distribution, and iteration completion. Schema v16 preserves cancellation separately from scheduler lateness; schema v17 persists scheduler admissions and requires planned = admitted + dropped and admitted = worker-started iterations. Open-arrival reports identify monotonic planned-slot-to-admission lag and expose sample count, p50, p95, and maximum. Admission closes at the monotonic observation deadline even if timer delivery is delayed; already admitted journeys may finish during the bounded drain. Scheduling accuracy under operating-system load remains uncalibrated. A partly open model with independently arriving sessions and dependent steps within each session is not implemented.

**Virtual-user runtime.** Each actor can maintain its own configured cookie and place in a sequential workflow. Closed-loop VUs keep one deterministic weighted-profile assignment for the run; arrival mode selects a profile per planned journey start. Steps can extract a bounded header or JSON Pointer value for later steps in the same journey. Response assertions are supported. Explicit cleanup suffixes run after business failures and external cancellation within the reserved drain budget. Dynamic login/CSRF recording and a full partly open session model remain planned.

Scenario and profile timing may use a fixed between-step pause, a bounded seeded uniform range, or a bounded seeded discrete sample list with repeated entries for relative frequency. Closed-loop choices depend on actor and journey ordinal; arrival choices depend on scheduler callback ordinal, independent of which worker receives the journey. Actual sleep times remain observed wall time and are subject to cancellation and host scheduling.

**HTTP execution.** Use Go's networking primitives for HTTP/TLS. Damocline itself owns the load-control logic, sequencing, timing, measurement, failure accounting, and safety guards. Handle keep-alive, redirects, deadlines, and response-body cleanup explicitly. Scenarios select `connection_policy` as `reuse` (the default) or `new_per_request`; the engine applies it to its shared transport and persists it in schema-v14 reports and workload fingerprints. Preflight schema v6 measures five fixed HTTP request shapes at three exact rates under both connection policies; schema v8 preserves those 30 exact profiles and adds three trusted HTTPS GET profiles at 2, 5, and 10 starts/s using connection reuse. The preflight stores each native run plus independent server request/body/TCP counts and client TLS-handshake counts. Its certificate is ephemeral, self-signed and local to the parent/child fixture process pair. Historical preflight schemas v1-v7 retain their original HTTP matrices. This qualifies only the named short loopback profiles; it does not calibrate TLS timing precision under load or remote endpoint behavior. Schema-v15 run reports can include independent counters for the calibrator-owned child-process soak; only that exact loopback run can reach `VALID_WITHIN_ENVELOPE` when all persisted dimensions and generator health reconcile. Schema-v7 run reports include per-step client-observed timing totals for rate wait, DNS, TCP connect, TLS, request write, first response byte, body read and full completion; schema v8 adds structured status and failure counts; schema v10 records generator sampler cadence and collection wall time; schema v11 includes a redacted-by-construction workload fingerprint for offline comparison; schema v12 records per-step complete, interrupted, and oversized body-read counts plus min/max/total bytes for complete bounded bodies; schema v13 adds reconciled per-step and explicit-profile request/journey ledgers in each observation window; schema v14 records the connection policy; schema v15 can persist the controlled-reference counter evidence; schema v16 records cancelled planned arrivals; schema v17 records scheduler admissions. Body byte counts exclude content and describe bytes returned by the response-body reader, not wire traffic. They do not establish endpoint identity or workload equivalence. Timing totals do not isolate server processing, and phase accuracy is not calibrated under load. The fingerprint excludes resolved credentials and environment-backed body values, so it does not prove runtime data equivalence.

**Capacity explorer.** Run bounded repeated probes against explicit error and latency targets, and optionally attempt an exact business target. Its short experiments report observed passing and failing levels; they do not establish a sustained or statistically certified capacity boundary.

**Capacity campaign.** Execute separate bounded warm-up, observation, optional spike and recovery runs across repeated trials. Campaign schemas v2-v6 retain the effective wall-time cap, every attempted phase and its observed/delivery classification, and a coarse observation-window drift screen; schema v3 records successful completed-journey throughput spread, schema v4 adds an optional final soak, schema v5 persists bounded drift thresholds, schema v6 can record an explicit staging long-run opt-in, schema v9 records an optional 0�5 minute cooldown and a unique random `run_id` per trial, and schema v10 adds execution state plus an optional pending trial. Open-arrival campaign schema v5 records the cooldown and trial IDs; schema v6 adds the same checkpoint state. `--out` is atomically updated after each phase report and once more with the terminal result. A `RUNNING` artifact carries `INCONCLUSIVE` as its top-level outcome and the current trial as `IN_PROGRESS`; offline audit retains completed phase data while explicitly refusing to infer the campaign's final outcome. A forced stop during a phase cannot save that phase until its runner returns. Cooldown is applied between passing trials and included in the wall-time budget; cancellation during cooldown is retained as an aborted next trial. Trial IDs group phases within one artifact and do not identify an environment or authenticated session. Application-specific test-data resets and session rotation remain caller responsibilities. Long-run phases remain capped at 30 minutes, the total budget at 2 hours and evidence windows at 120; the ordinary 3-minute run and 15-minute campaign limits remain unchanged. Every non-dry campaign requires `--out`; dry-run previews remain traffic-free and do not write an artifact. Long-run mode also requires an explicitly declared staging environment, authorization, `--allow-long-run`, `--staging-confirmed` and explicit `--budget`. The offline demand planner checks the exact saved phase sequence, load, duration, classification and recomputed screen using the saved policy before using a passing campaign. Environment declarations are not independently verified, and missing equivalent generator evidence still prevents ordinary target campaigns from certifying capacity.
The `internal/arrivalexplorer` package and `explore-arrival` command search scheduled open-loop journey starts/s in a separate result format from the closed-loop VU explorer. The scenario's `users` value remains its worker limit, while `max_rps` remains the HTTP request-start governor. When an exact local calibration is supplied, the search is restricted to compatible measured rate profiles; the requested minimum and in-range business target must be covered, and the effective maximum is the highest compatible rate. Schema-v2 results persist the requested bounds and calibrated set, and offline goal validation rejects probes outside it. This qualifies only local generator delivery for the matched short profiles; it does not validate target identity, response behavior or sustained duration. Dropped work, inadequate samples, generator pressure, or a binding request governor produces inconclusive evidence; a result is not a conversion between these units or a capacity certification.

The `internal/arrivalcampaign` package and `arrival-campaign` command run repeated bounded open-arrival phases at an exact base starts/s rate, with optional warm-up, higher-rate spike, recovery and final soak. Every non-dry campaign requires `--out` to retain all attempted phase evidence. They preserve each native phase report and use the configured observation windows and existing coarse drift screen. Schema v2 supports the same explicitly declared staging long-run mode and limits as closed-loop campaign. Schema v5 also persists the bounded inter-trial cooldown and per-trial IDs; its independent artifact is checked offline by `capacitygoal` for exact demand, distinct IDs and phase consistency. This evidence remains conditional on the saved workload and LIMITED native report quality; it is not certification.

Arrival demand planning accepts peak scheduled starts/s, projected growth and reserve. It inserts the calculated exact rate into the bounded exploration when requested, and `goal --file` can reassess a saved artifact offline. The assessor verifies native run evidence and never interpolates; `LIMITED` quality remains insufficient for a positive demand finding. It does not certify sustained capacity.

**Metrics pipeline.** Report request and completed-journey distributions, failures, arrival accounting, scheduler lag, sampled Go-runtime plus supported OS process health for the generator, optional request time windows, and a conditional IID-assumption P95 rank interval. Schema-v13 observation windows retain per-step request metrics and completed-journey metrics for explicit profiles, and evaluate their configured criteria independently of aggregate request metrics. Interrupted journeys are counted as cancelled and make an otherwise passing run inconclusive; their partial duration is not presented as a completed journey latency. Schema-v10 reports also record sampler interval, maximum observed sample gap, and wall time spent collecting samples. Schema-v25 can retain a bounded timestamped timeline from an explicitly configured Prometheus-text endpoint during a run; closed-loop and open-arrival campaign phases each keep their own timeline. Scrape labels are discarded, query strings and URL credentials are rejected, failures are counted, and a campaign-wide ceiling bounds attempts. These auxiliary requests do not enter the engine's RPS governor or load counters. They provide manual alignment only; values are not interpreted as causes and do not change run or campaign verdicts. A run may attach a bounded local calibration artifact; the shared validator checks its preflight schema, stage ledgers and scheduler-lag observations, then stores only sanitized provenance and declared-dimension findings. For ordinary runs, the fixed fixture cannot prove target response shape or endpoint identity, so attached evidence remains inconclusive. The calibrator separately observes its own child-process fixture and can qualify only that controlled 30-second soak. Windows and percentile intervals do not establish steady state or account for correlated samples. Reports also record a request-boundary Little's Law consistency signal when average in-flight sampling, throughput, and mean latency share the configured observation window.

The local report dashboard accepts one run or campaign artifact. Campaign stages remain separated by trial and phase, and the dashboard distinguishes closed-loop VUs from scheduled open-arrival starts/s. Within each phase it overlays HTTP-window p95 at each window's UTC midpoint with stored application-metric samples on a shared UTC axis, using independent value scales and individual points. Current run start timestamps retain subsecond precision; older artifacts may have only second precision. No clock-offset correction, interpolation, SLO mapping or cause attribution is performed. Input size is bounded and saved run/phase schemas are validated before rendering. The listener remains loopback-only and read-only.

`report export` validates saved run, closed/open-arrival campaign, and closed/open-arrival exploration evidence before writing a separate allowlist format for sharing. It retains aggregate counts, latency summaries, phase/window timing and workload units while omitting target addresses, routes, arbitrary labels, free text, fingerprints, absolute timestamps and custom metric names/values. Exported artifacts are descriptive, not native inputs to capacity assessors. The selected output uses the atomic, size-limited report writer; source files are never rewritten.

Calibration attachment derives per-step response-size and coarse request-latency guardrail dimensions from the run fields. Neither match establishes response distributions, per-window stability, endpoint identity, or workload equivalence; overall measurement quality remains limited while these are unknown.

**Optional telemetry adapters.** Collect host, Docker, database, or cloud metrics with consent and configured permissions. An absent metric is unknown, not proof of health. Avoid transferring secrets or unrestricted production logs.

**Reporting.** Store scenario/environment identity, constraints, time window, achieved workload, results, variability, and diagnostic limitations. Distinguish direct observations, correlations, and unverified hypotheses.

## Hosting models

- **HTTP-only:** reachable, authorized applications on VPS, dedicated servers, Docker, Kubernetes, PaaS, or serverless.
- **Host/container observability:** optional, permissioned Linux and Docker collectors.
- **Cloud/orchestrator observability:** future cloud provider and Kubernetes adapters.
- **Browser experience:** future browser-based journey execution, independent from protocol-level load.

The application-under-test may comprise multiple services. There is no single physical "server limit" when autoscaling and managed dependencies are involved; the report should identify the tested configuration and first observed limiting condition.

## Safety must precede load generation

The shipped test commands require explicit authorization for traffic and enforce configured duration, concurrency/rate ceilings, request deadlines, and opt-in write operations. Prefer staging and synthetic data; these controls bound tests but do not establish target ownership or guarantee that every workload is safe for every application.

## Development boundaries

Keep a small Go CLI and standard-library-first core. Add deterministic unit/integration tests using local HTTP servers. Only add dashboards, distributed workers, and automatic infrastructure diagnostics after correct single-node scheduling and measurement are demonstrated.

## Windowed journey evidence

Schema-v22 reports keep completed-journey counters and latency distributions in each observation window for legacy workflows and weighted profiles. `internal/capacityplan` evaluates the whole-run journey ledger and each window against the declared latency and error objectives, in addition to request and step ledgers. Window counters reconcile against the run ledger; explicit profile counters reconcile to the aggregate journey window. Campaign stability screening requires sufficient completed journeys in every window and checks coarse full-journey latency and throughput drift. This supports a cautious offline demand assessment and does not certify sustainable capacity.

Schema-v26 changes weighted-profile selection for new runs to happen at every journey start in both closed-loop and open-arrival modes. Smooth weighted round-robin keeps the selected-start mix independent of workflow length and response time. The report records each workflow's selected starts, worker-started journeys, distinct VUs observed, and outcomes; current-schema quality checks reconcile those counts with aggregate scheduler and journey ledgers. Older reports continue to use their original closed-loop actor assignment semantics. A VU's cookie jar remains actor-local and persists while that actor changes workflows, so this does not create per-workflow authenticated identities.

Offline campaign audit recomputes per-trial request/journey summaries and run-to-run spread from saved base-load observation reports, rejecting a persisted spread that disagrees with its phase sources. These summaries remain descriptive and do not establish independence, stationarity, or a confidence interval.
